Python Web App Deployment Without Losing Your Will to Live: Reflex + Docker + Caddy

Build, Ship, Pray: Dockerizing Reflex Apps with Caddy Like a Functional Adult

Gwang-Jin
13 min read
·
3 days ago

Deploying web apps is a scam.

You write some perfectly decent Python code. It runs on your laptop. You feel powerful.

Then you “deploy” it — and suddenly you’re three Dockerfiles deep into despair.

Ports refuse to open. Firewall rules mock you. Python versions argue like drunk uncles at Thanksgiving.

You find yourself asking philosophical questions like:

“Was mankind supposed to deploy software?”

“Is Docker a metaphor for capitalism?”

(Spoiler: Yes.)

Then some guy on Reddit (username probably ends in 69420) mumbles:

“Docker bro. Just containerize it.”

“It’ll work anywhere,” they said.

It won’t.

But at least your failures will be consistent across operating systems, like a true professional.

Meanwhile, you still need a web server.

Nginx? Apache? Too much XML-flavored sadness.

Welcome Caddy: the ADHD golden retriever of web servers.

  • Free SSL?
  • Auto-config?
  • Suspiciously easy to use?

Absolutely. Trust issues later. Less typing now.

And then there’s Reflex.

“Build web apps in pure Python!” they said.

What they meant:

  • Python.
  • Also install bun. (Nobody can explain why. — Ok, joke. Bun is a single binary with hardly other dependencies. Therefore it was taken instead of npm & co. For slickness.)
  • Also install half of Node.js.
  • Also pray.

Nothing pure remains. However, here one short view over — “Why Reflex? why not simply use Flask?”

Today, we’re going to duct-tape these ingredients together:

  • Docker Compose (the puppet master)
  • Caddy (the bouncer handing out HTTPS like candy)
  • Reflex (the kid you reluctantly babysit)

The goal:

Make it “work enough” that you can pretend you understand DevOps on your résumé.

Prerequisites: (The Cover Charge for Entering This Nightclub of Pain)

You must have:

  • Docker installed
  • Docker Compose installed
  • Some residual hope

If you don’t, go search “install Docker Ubuntu/Mac/Windows” and lose the next 45 minutes of your life.

This guide assumes you are stubborn enough to have Docker working already.

I will not save you from yourself.

Quick Start

1.) Clone the Repository:

git clone https://github.com/gwangjinkim/reflex-caddy-docker.git
cd reflex-caddy-docker

2.) Edit your Caddyfile and rxconfig.py: Make sure the domain and app names match your real deployment.

3.) Build and Run:

docker compose build --no-cache
docker compose up

4.) Enjoy: Open https://yourdomain.com and behold your creation.

Step 0: Make Folders Like You’re a Real Developer

mkdir reflex_container
cd reflex_container
mkdir app
mkdir app/assets app/my_reflex_app

Look at you, creating structure.

Pretend your life is this organized too.

Step 1: Write Code No One Will Appreciate

We want to generate this structure:

.
├── Caddyfile
├── app
│   ├── Dockerfile
│   ├── assets
│   ├── my_reflex_app
│   │   ├── __init__.py
│   │   └── my_reflex_app.py
│   ├── requirements.txt
│   └── rxconfig.py
└── docker-compose.yml

4 directories, 7 files

Create the mighty app with nano or your editor of choice:

nano app/my_reflex_app/my_reflex_app.py

Paste this literary masterpiece:

# app/my_reflex_app/my_reflex_app.py
import reflex as rx

def index() -> rx.Component:
    """The main page. Don't expect much."""
    return rx.center(
        rx.vstack(
            rx.heading("Behold! Code in a Box!", size="8"),
            rx.text("It's probably broken somewhere else."),
            align="center",
            spacing="7", # Arbitrary spacing. 
            font_size="2em", 
        ),
        height="100vh", # fill the screen
    )

# Boilerplate to make Reflex happy.
app = rx.App(
    theme=rx.theme(
        appearance="light", has_background=True, radius="large", accent_color="teal"
    ),
)
app.add_page(index, route="/") # The main page route.

Save and Exit: In nano, that's Ctrl+X, then Y, then Enter. Don't mess it up.

This will work until Reflex releases an update tomorrow and ruins everything.

touch app/my_reflex_app/__init__.py

Appeasement Ritual: Python needs this empty file to see the folder as a “package”. Just do it.

Step 2: appease Reflex with a config file

Create app/rxconfig.py by:

nano app/rxconfig.py .

Paste this necessary evil:

# app/rxconfig.py
import reflex as rx
import os # Gotta talk to the operating system. Spooky.

# Figure out the public URL from an environment variable.
# Defaults to 'http://localhost' if you forget to set it later.
# Use 'https://your-domain.com' for real deployments, obviously.
deploy_url = os.environ.get("DEPLOY_URL", "http://localhost")

config = rx.Config(
    app_name="my_reflex_app", # The app's glorious name.
    # Tell Reflex how the outside world sees it. Crucial. Don't skip.
    frontend_url=deploy_url,
)

Save and Exit: Ctrl+X, Y, Enter.

Congratulations: you have now outsourced your future bugs to environment variables.

DevOps approved.

Step 3: The Dependency List (What Your App Demands)

A file listing all the Python libraries your app needs to function (or, in this case, just the one).

Create requirements.txt:

nano app/requirements.txt

Add the One True Dependency (for now):

reflex

Save and exit.

One package now.

Five indirect JavaScript nightmares later.

Step 4: Write a Dockerfile and Cry Quietly

Make sure, you are in the main reflex_container folder.

Create the Docker file inside the app:

nano app/Dockerfile

Paste the Arcane Incantations:

# app/Dockerfile

# Start with a basic Python box. 'Slim' means fewer toys included.
FROM python:3.12-slim

# Environment variables to make Python slightly less annoying in Docker.
ENV PYTHONDONTWRITEBYTECODE 1 # No useless .pyc files.
ENV PYTHONUNBUFFERED 1       # Logs appear faster, maybe.

# Where the code will live inside the box.
WORKDIR /app

# Install system stuff needed because 'slim' is TOO slim.
# Reflex needs 'unzip' and 'curl' to install its JavaScript friend 'bun'.
# Yes, the Python framework needs JavaScript tools. Don't ask.
RUN apt-get update && apt-get install -y --no-install-recommends \
    unzip \
    curl \
    # Clean up afterward to keep the box slightly less bloated.
    && rm -rf /var/lib/apt/lists/*

# Now copy everything into the `/app` folder
COPY . .

# Update pip itself, then install the demands.
RUN pip install --no-cache-dir --upgrade pip
RUN pip install --no-cache-dir -r requirements.txt


# Tell Docker which ports the app *inside* the box will try to use.
# 3000 for the web page part (frontend), 8000 for the Python brain (backend).
EXPOSE 3000
EXPOSE 8000

# The command to run when the container starts.
# This starts Reflex in 'dev' mode (slow, but reloads code changes).
CMD ["reflex", "run", "--frontend-port", "3000", "--backend-port", "8000"]

Save and exit.

Notice:

  • pip is used.
  • We install unzip because Reflex secretly downloads bun and cries without it.
  • And we need curl, too.

Step 5: Caddyfile — Because Nginx Can Go Cry Somewhere Else

nano Caddyfile in the project root:

# Caddyfile

{
    # IMPORTANT: If using a real domain, uncomment this and put your email.
    # Let's Encrypt (who gives the free HTTPS certs) needs it.
    email your-actual-email@example.com
}

# The address Caddy listens on. Change 'localhost' to your real domain(s).
# You can list multiple domains separated by spaces.
# change localhost to `yourdomain.com www.yourdomain.com`
localhost { 

    # Optional: Make responses smaller. Saves maybe 0.01 cents.
    encode zstd gzip

    # Identify requests that need to go to the Python backend (port 8000).
    @backend_routes path /_event/* /ping /_upload /_upload/*

    # Handle those backend requests.
    handle @backend_routes {
        # 'app' is the name of our Reflex service in docker-compose.yml
        reverse_proxy app:8000
        # header_up X-Forwarded-Proto {scheme} # Caddy usually does this implicitly now
    }

    # Handle everything else (the frontend UI).
    handle {
        # Send these to the frontend server (port 3000 in the app container).
        reverse_proxy app:3000
        # header_up X-Forwarded-Proto {scheme} # Caddy usually does this implicitly now
    }
}

If you squint, you can almost pretend this makes sense.

Step 6: Compose Yourself (docker-compose.yml)

This file defines the services (your app, Caddy), connects them with a network, sets up persistent volumes (so Caddy doesn’t forget its HTTPS certs), and passes that crucial DEPLOY_URL to your app.

Navigate: Still in reflex_container.

Create the Compose File:

nano docker-compose.yml

Paste the Grand Plan:

# docker-compose.yml
# No version needed at the top anymore, Compose V2 assumes latest.

services:
  # The Reflex App Service - codename 'app'
  app:
    build:
      context: ./app # Build using the Dockerfile in ./app
      dockerfile: Dockerfile
    container_name: reflex_app_container # So you can find it later
    volumes:
      # Link local ./app folder to /app inside container.
      # Change code locally -> changes appear in container (for dev mode). Magic? No, just mounts.
      - ./app:/app
    environment:
      PYTHONUNBUFFERED: 1 # For logs
      # *** THE IMPORTANT BIT ***
      # Set this to how people access your site.
      # For local testing: "http://localhost"
      # For real site: "https://yourdomain.com"
      DEPLOY_URL: "http://localhost"
    networks:
      - reflex_network # Connect to our private network

  # The Caddy Service - codename 'caddy'
  caddy:
    image: caddy:latest # Use the official Caddy image
    container_name: caddy_proxy_container
    restart: unless-stopped # Keep it running, maybe it's useful
    ports:
      # Connect HOST ports to CONTAINER ports. This is how the outside world talks to Caddy.
      - "80:80"      # HTTP
      - "443:443"    # HTTPS
      - "443:443/udp" # HTTP/3 (because we're fancy?)
    volumes:
      # Give Caddy our config file.
      - ./Caddyfile:/etc/caddy/Caddyfile
      # Let Caddy save its homework (certs, state) persistently.
      - caddy_data:/data
      - caddy_config:/config
    networks:
      - reflex_network # Also on the private network
    depends_on:
      - app # Don't start Caddy until 'app' is at least trying to start.

# Define the private network for containers to chat.
networks:
  reflex_network:
    driver: bridge # Standard virtual network

# Define the persistent storage spots.
volumes:
  caddy_data:
  caddy_config:
  • CRITICAL: Go back and edit that DEPLOY_URL under app.environment if you're using a real domain. Use https://yourdomain.com.
  • Save and Exit.

Translation:

Caddy and your app are now stuck together on a little fake private LAN.

They will complain at each other, not at you.

Step 6.5: Don’t Forget to Open Ports in the Firewall!

This is an essential step, especially if this is the first time ever for you to deploy a website from the server you are using right now. (Forgetting this costed me many hours of confusion).

We use ufw — if not installed, install it: sudo apt install ufw .

Check:

sudo ufw status

Open ports for OpenSSH, 80 (http),443/tcp (https):

sudo ufw allow OpenSSH
sudo ufw allow 80,443/tcp

# check by:
sudo ufw status

# it should show sth like:
Status: active

To                         Action      From
--                         ------      ----
OpenSSH                    ALLOW       Anywhere                  
80,443/tcp                 ALLOW       Anywhere                  
OpenSSH (v6)               ALLOW       Anywhere (v6)             
80,443/tcp (v6)            ALLOW       Anywhere (v6)



#########
# if not, probably reset and enable new and do the steps above
sudo ufw reset
sudo ufw enable

# if the ports for 3000 and 8000 are open, you have to close them
sudo ufw deny 3000/tcp
sudo ufw deny 8000/tcp

# you want only the standard ports 80 and 443 be presented to the outside
# of the server!

Step 9: When It Inevitably Fails

  • Check Reflex logs:
docker compose logs app
  • Check Caddy logs:
docker compose logs caddy

Look for words like error, panic, or oh no.

These are your clues.

Bonus Round: Add Real Domains and Real Consequences

  • Update Caddyfile with yourdomain.com www.yourdomain.com
  • Set real DEPLOY_URL to “https://yourdomain.com"
  • Make sure DNS is pointing correctly.

Reminder:

If you screw this up, Caddy will try HTTPS anyway and fail miserably.

You will not get sympathy from your future self.

Like so often, I thought this is a story of 10–20 minutes. It came out as an entire-lunch-and-afternoon-occupation (sigh). The reason was that uv worked perfectly but the virtual environment folder of uv — while present during creating of the Docker container — mysteriously disappears when the container is running.

First, I’ll give you the solution. In the next section, I will tell you the details.

We can apply this into our Dockerfile by:

# app/Dockerfile

# Start with a basic Python box. 'Slim' means fewer toys included.
FROM python:3.12-slim

# Environment variables to make Python slightly less annoying in Docker.
ENV PYTHONDONTWRITEBYTECODE 1 # No useless .pyc files.
ENV PYTHONUNBUFFERED 1       # Logs appear faster, maybe.

# => Install uv globally by copying the binary from the official container
COPY --from=ghcr.io/astral-sh/uv:latest /uv /uvx /bin/

# Now copy all of your brilliant code.
COPY . .

# Install system stuff needed because 'slim' is TOO slim.
# Reflex needs 'unzip' and 'curl' to install its JavaScript friend 'bun'.
# Yes, the Python framework needs JavaScript tools. Don't ask.
RUN apt-get update && apt-get install -y --no-install-recommends \
    unzip \
    curl \
    # Clean up afterward to keep the box slightly less bloated.
    && rm -rf /var/lib/apt/lists/*

# Where the code will live inside the box.
WORKDIR /app/app

# Create a virtual environment using uv
RUN uv venv

# Install your dependencies inside that venv
RUN uv pip install --system -r requirements.txt

# Tell Docker which ports the app *inside* the box will try to use.
# 3000 for the web page part (frontend), 8000 for the Python brain (backend).
EXPOSE 3000
EXPOSE 8000

# The command to run when the container starts.
# This starts Reflex in 'dev' mode (slow, but reloads code changes).
CMD ["uv", "run", "reflex", "run", "--frontend-port", "3000", "--backend-port", "8000"]
  • COPY — from=ghcr.io/astral-sh/uv:latest /uv /uvx /bin/ installs uv directly
  • uv venv activates the virtual environment — locally, a .venv folder will be created inside your project folder which will contain all installations including the Python version if deviating from the current sytem Python version
  • uv pip install ... installs packages into .venv — in this case --system was essential! Without it reflex was installed but when the container was running, no .venv was there and no reflex could be found!
  • uv run reflex run ... the uv run is equivalent to source .venv/bin/activate but let’s the virtual environment embed only the reflex run command.

After changing the Dockerfile, you do:

docker compose build --no-cache
docker compose up

When it complains that there is already a container with the same name:

docker rm -f caddy_proxy_container

# clean just your project
docker compose down -v --remove-orphans

#  Clean up ALL unused stuff globally (but NOT running containers)
docker system prune -a --volumes

# TOTAL DESTRUCTION (nuclear option)
docker system prune -a --volumes
docker volume prune
docker network prune
docker builder prune

# or even:
docker container prune
docker image prune -a

The last commands are for resetting Docker almost completely.

How uv Taught Me to Distrust Everything, Including Myself

You know what’s fun? Spending literal hours debugging a Docker container because a tool pretends to create a virtual environment — and then casually throws it into a black hole right after.

Here’s what happened:

I naively assumed that uv venv would behave like a normal citizen. It didn’t.

It created a .venv during the Docker build phase — I even made it scream its existence with:

RUN uv venv \
    && echo "Checking if .venv was created:" \
    && ls -la /app/.venv

And guess what? .venv was there. Standing proud.

I was winning. Life was good.

Until I actually ran the container.

At runtime, .venv was gone. Reflex was gone. My will to live? Also gone.

Meanwhile, /app/ itself was still there — sitting there like an empty husk, like a crime scene after the body’s been removed.

Just enough left behind to mock me.

Dropping into the running container with:

docker compose run --rm app sh

I saw /bin/uv, /bin/uvx, but no .venv under /app/ thus no working reflex in the container.

Just the echo of bad decisions.

Turns out, unless you use --system, Reflex will disappear with .venv — doesn’t survive Docker’s layer magic. It’s created during build — then it vanishes at runtime faster than your free trial ending at midnight.

The fix? Install into the system Python inside the container directly:

RUN uv pip install --system -r requirements.txt

Now reflex installs to /bin/ as /bin/reflex, like a normal program, where it can’t sneak off and abandon you.

And suddenly, uv run reflex run … or reflex run … — both actually work.

Docker lesson #492:

If you don’t manually verify everything, assume it’s lying.
